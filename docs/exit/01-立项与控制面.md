# 01 · 立项：住宅出口控制面（Workers 侧）

> 日期：2026-10-25
> 状态：**M1（Workers 控制面）已实现并通过门禁**；M2 起需硬件。
> 上游设计：`抖音出口-技术路线.md`、资料库 `management-plane`。

---

## 1. 立项定义

**一句话**：把家里的 ESP32 变成一个「公网可调度、只转发不解析」的住宅 IP 出口，由 Cloudflare Workers 统一管节点、派任务、看指标、推固件。

**要解决的问题**

| 问题 | 现状 | 本项目的答案 |
|---|---|---|
| 没有公网服务器 | 只能靠 Cloudflare | Worker + DO，零机器 |
| 家庭宽带无公网 IP | NAT 后面 | ESP32 主动出站，反连 Worker |
| 目标站点认 IP 段 | 机房 IP 被风控 | 家用宽带出口 |
| 站点改版/加签 | 固件改一次烧一次 | 解析逻辑全在 Worker，改完 deploy 即生效 |
| 多台设备没法管 | 各自为政 | 控制面统一节点表 + 工具调用 + 面板 |

**非目标（明确不做）**

- 不做通用翻墙/代理给别人用
- 不做百万级设备调度（控制面是单实例 DO，家庭规模）
- 不试图伪装 TLS 指纹（硬件决定的极限，见 §7 风险）

---

## 2. 技术路线（确认版）

```
浏览器 ──POST /admin/api/call──▶ Worker 入口
                                    │
                                    ▼
                            Manager DO（全局单例）
                            节点表 / 工具表 / 任务流水
                                    │ DO-to-DO fetch
                                    ▼
                            Relay DO（按 tunnel 分实例）
                            复用现有 WS，下发 JSON 控制帧
                                    │ wss（常驻，ESP32 主动出站）
                                    ▼
                            ESP32-C6（家里）
                            https_fetch：建 TLS → 写原始 HTTP 字节 → 分块回传
                                    │
                                    ▼
                            目标站点（家用 IP 出口）
```

**关键决策与理由**

| 决策 | 选择 | 被否掉的做法 | 理由 |
|---|---|---|---|
| 解析放哪 | **Worker** | 放固件 | 站点改版只改 Worker，不用重烧 |
| 任务怎么下发 | **复用已有 WS 推 CALL** | HTTP 长轮询 25s | 再开一路等于同一份 TLS 握手干两遍，C6 那点 heap 经不起 |
| 控制消息格式 | **JSON 文本帧** | 扩二进制帧 | CALL 参数是结构化变长字符串，二进制要自己做 TLV，ESP32 还得手写解析 |
| 数据体回传 | **二进制 DATA 帧** | JSON base64 | 大字节流不能走 JSON，开销翻 1.33 倍且要额外缓冲 |
| 谁做 TLS | **ESP32（mbedtls）** | Worker 侧 `cloudflare:sockets` | `startTls()` 只能作用于 `connect()` 返回的本地 socket，**无法作用于 WS 消息流** |
| 控制面实例数 | **单例** | 每 tunnel 一个 | 节点表是全局决策依据，分散立刻出现分裂 |

## 3. 协议（v2）

### 3.1 二进制帧（数据面，**未改动**）

| 帧 | 值 | 布局 | 方向 |
|---|---|---|---|
| OPEN | 0x01 | `channel(1) ip(4) port(2)` | 用户 → ESP32 |
| OPEN_OK | 0x02 | `channel(1)` | ESP32 → 用户 |
| DATA | 0x03 | `channel(1) payload` | 双向 |
| CLOSE | 0x04 | `channel(1)` | 双向 |
| WOL | 0x05 | `mac(6)` | 用户 → ESP32 |

### 3.2 JSON 控制帧（控制面，**新增**）

| 消息 | 方向 | 载荷 |
|---|---|---|
| `hello` | 设备 → Worker | `node / model / fw / tools[] / capacity / heap / rssi / ip` |
| `hb` | 设备 → Worker | `heap / rssi / up / conns / fw` |
| `call` | Worker → 设备 | `id / tool / args{} / ch`（`ch` = 结果体回传用的 DATA 通道） |
| `result` | 设备 → Worker | `id / ok / err? / meta{status,bytes,ms,host}` |

**通道分配**：工具调用从 192~255 取，避开用户通道（一般 0~10）。释放后回收。

**时序**：`call` → `DATA × N`（结果体，4096B/块）→ `result`（收尾）。超时 20s，超时后迟到的 `result` 直接丢弃。

## 5. 面板数据展示设计

### 5.1 为什么推翻第一版

第一版是「运维仪表盘」：首屏四格 KPI 全是 `在线节点 / 今日调用 / 成功率 / 最低堆余量`。

问题在于**打开这个页面的人想知道的不是这些**。真实使用场景是一只手掌着手机、
想确认「现在能不能用」然后「让它帮我取个网页」。而第一版要求先选 tool 再填 host 和
path 分两栏——那是把固件和 Worker 之间的契约直接暴露给使用者。

第二版的信息顺序按「我需要知道什么」重排：

| 顺序 | 区块 | 回答的问题 |
|---|---|---|
| 1 | **一句话结论**（大字 + 底色） | 现在能不能用？绿=能，黄=还没连上，红=连不上 |
| 2 | **三个动作按钮** | 帮我干件事（抓网页 / 唤醒电脑 / 看网络） |
| 3 | **今天** | 今天干了多少、成没成 |
| 4 | **最近干了什么** | 用人话，不是 `https_fetch 200 12345` |
| 5 | **谁在用** | 哪把 key 用掉多少额度 |
| 6 | **技术细节**（折叠） | 排障才需要：heap / RSSI / 固件 / 工具表 / 安全项 |

### 5.2 人话映射

面板上不该出现固件与 Worker 之间的术语，所以有一层映射：

| tool | 面板文案 |
|---|---|
| `https_fetch` / `http_get` | 抓网页 |
| `net_info` | 查网络 |
| `dns_lookup` | 查域名 |
| `tcp_probe` | 探端口 |
| `wol` | 唤醒电脑 |
| `ota_apply` | 升级固件 |

时间也一样：「3 秒前」「12 分钟前」比 `12:07:43` 好读；离线时长说「3 分钟前还有消息」
比 `silentFor: 180` 直观。

### 5.3 状态文案（三种状态都不许含糊）

| 状态 | 大字 | 副文案 |
|---|---|---|
| 无节点记录 | 还没有设备连进来 | 板子上电后会自动连上并自报家门，通常十几秒内出现。 |
| 有记录但全离线 | 连不上了 | 最后一次收到消息是 N 分钟前。可能是断电、断网，或者路由器把它踢了。 |
| 有节点在线 | 在线，随时能干活 | ESP32-C6 N8 · N 秒前还有消息 · 上次干活 N 秒前，用了 N 毫秒 |

### 5.4 视觉约束

- 只两档字重（400/500），字号阶梯 10/11/12/13/15/22/26
- 间距走 4 的倍数；卡片圆角 12/14
- 深浅色靠 `prefers-color-scheme` 切 CSS 变量，**不提供手动开关**（少一个状态少一处不一致）
- 所有图形自己画 SVG，零外链（`*.vercel.app` 在这台机器上直接裂图）
- 从设备来的字符串一律走 `esc()` 再进 innerHTML
- 折叠图标用 CSS 三角形而非 `▸` 字符（中文字体里那个字符在部分设备上会掉成方块）

### 5.5 交互验证

面板不能只靠截图验收——截图只能证明"渲染出来了"，证明不了"点了会发生什么"。
`test/panel-interact.mjs` 用 CDP 真的点按钮、真的填输入框、真的等结果，
然后断言结果区出现了设备回答。13 项，全绿才算完成。
- 布局用 `minmax(0,1fr)` 而不是 `1fr`：后者被 `white-space:nowrap` 的内容撑开会导致移动端横向溢出（本轮踩过，已实测 331/360/375/414/768 五个宽度均 0 溢出）

### 5.3 空态

不显示空白骨架，直接说清楚为什么空：
- 无设备：「还没有设备注册过 / ESP32 第一次连上并发出 hello 后，自动出现在这里」
- 无任务：「暂无任务 / 在下面命令台发一条，这里会出现完整链路记录」

## 6. 部署清单

```bash
cd F:/esp32/tunnel/worker

# 1) 类型检查（门禁）
node ./node_modules/typescript/bin/tsc --noEmit

# 2) 注入密钥（生产必须）
npx wrangler secret put TUNNEL_TOKEN   # 设备 ↔ Worker 共享密钥，同时是 /_call 的密钥
npx wrangler secret put ADMIN_TOKEN    # 面板口令

# 3) 部署（Manager 的 v2 migration 会随首次 deploy 自动应用）
CLOUDFLARE_API_TOKEN=*** CLOUDFLARE_ACCOUNT_ID=YOUR_CF_ACCOUNT_ID \
  ./node_modules/.bin/wrangler deploy

# 4) 打开
#    https://wol.zjql.qzz.io/admin?token=<ADMIN_TOKEN>
```

> ⚠️ 域名铁律：**不要用 `*.workers.dev`**，国内 DNS 污染会解析到 Facebook IP，ESP32 与浏览器都连不上。必须走 `wol.zjql.qzz.io` 自定义域名。

**接口一览**

| 路径 | 用途 |
|---|---|
| `GET /admin` | 面板（认会话 Cookie 或 `Authorization: Bearer`，**不接受 `?token=`**） |
| `POST /admin/login` | 口令换会话 Cookie（口令只在这一步出现，且只在 POST body 里） |
| `GET /admin/api/snapshot` | 面板数据快照 |
| `POST /admin/api/call` | `{nodeId?, tool, args, timeoutMs?}` → 一次工具调用 |
| `POST /admin/api/hello` | 内部：Relay 转发设备注册 |
| `POST /admin/api/hb` | 内部：Relay 转发心跳 |
| `GET /admin/api/nodes` | 节点原始列表 |
| `POST /relay/_call` | 内部：Manager → Relay 下发（`x-internal` 校验） |

## 7. 风险与止损

| # | 风险 | 应对 |
|---|---|---|
| 1 | 目标站点加签（已知：`a_bogus` / `msToken`） | 解析在 Worker，可随时换策略；M4 设止损点 |
| 2 | mbedtls TLS 指纹 ≠ 浏览器 | 无解，只能换硬件（旧安卓 Termux + curl-impersonate）；协议不变 |
| 3 | C6 单核 160MHz / ~320KB 可用 heap | `capacity` 限 2；面板 heap 曲线就是为此存在 |
| 4 | 免费版 Workers：同时 6 连接、100s 无数据切断 | 大文件分块 + 断点续传，不中转超 512KB |
| 5 | Brownout（已实测过） | 必须独立供电，别走笔记本 USB |
| 6 | 家庭 IP 被打标记 | 严格限频，不做批量 |

## 9. M2：ESP32-C6 固件（真机实测）

固件 `arduino/ESP32_C6_Exit/ESP32_C6_Exit.ino`，一键编译烧录脚本 `F:/esp32/upload-c6.bat`。

### 9.1 硬件实测

| 项 | 实测值 |
|---|---|
| 芯片 | ESP32-C6 (QFN40) rev v0.1，单核 160MHz + LP core |
| Flash | **8MB**（GD，JEDEC `c8 4017`），应用分区 3,342,336 字节 |
| 串口芯片 | **CH343**（`VID_1A86&PID_55D3`）→ COM4 |
| MAC | `F0:F5:BD:02:F8:CC`（node id 取后三字节 → `c6-02f8cc`） |
| 固件占用 | 1,196,032 字节（**35%**）—— 对比 D0WD 的 91%，OTA 槽终于有余量 |
| 全局变量 | 44,332 字节；boot 后 free heap **374,928 / largest 352,244** |
| Wi-Fi 后 | free 320,676 / largest 303,092 |
| WS(TLS) 连上后 | free 317,816 / largest 294,900 |

TLS 会话的真实成本（每次调用峰值，串口实测）：

```
[call] heap=317148 largest=294900
[fetch] www.baidu.com/ -> 200, 227 bytes, 0 hops, 225ms
[call] done heap=312112 (peak drop 5036)
```

即 **单次 HTTPS ≈ 掉 4.6~5KB 堆，结束后回到 312KB**，30 次连续调用 heap 曲线平直，无泄漏。
`largest` 会从 294,900 一次性降到 245,748 并稳定在那里 —— 这是第一次 TLS 把一个大块切碎的正常结果，不是泄漏。

### 9.2 编译与烧录参数（照抄，别自己改）

```
FQBN = esp32:esp32:esp32c6:PartitionScheme=default_8MB,UploadSpeed=115200
额外 = --build-property "build.flash_size=8MB"
```

两个坑都是实测撞出来的：

1. **`build.flash_size` 在核心里硬编码成 4MB，而 C6 没有 `FlashSize` 菜单。**
   只选 `default_8MB` 分区表 → 分区表写进去了，但 bootloader 仍按 4MB 判越界：
   `partition 3 invalid - offset 0x340000 size 0x330000 exceeds flash chip size 0x400000`
   → 无限重启。必须显式 `--build-property "build.flash_size=8MB"`。
2. **FQBN 多选项之间是逗号，不是冒号。**
   `PartitionScheme=...,UploadSpeed=115200` 对；写成两个冒号会直接报 `not an FQBN`。

### 9.3 工具范围

| 工具 | 行为 |
|---|---|
| `https_fetch` | TLS GET/POST，跟随最多 3 跳重定向，body 边读边发 DATA（不在内存攒整包） |
| `http_get` | 同上，明文 80 端口 |
| `net_info` | 返回芯片/堆/RSSI/IP/网关/DNS/MAC/运行时长，用于面板与排查 |
| `dns_lookup` | `WiFi.hostByName` 解析并计时 |
| `wol` | 魔术包广播（复用 v3 逻辑，端口 9/7 双发） |

**明确不做**（写清楚，免得以后以为漏了）：

- **不做 TCP 隧道**：收到 `OPEN` 一律回 `CLOSE`。本固件是应用层出口，TCP 隧道仍由 `ESP32_WOL_Tunnel` 承担。
- **不解 gzip**：请求强制 `Accept-Encoding: identity`。板子扛不动 inflate，压过的字节拿回 Worker 也只能原样转发。解 chunked 是做的。
- **不校验证书**：C6 上没有 CA 包，mbedtls 指纹本来也和浏览器不同，校验与否都不改变「这是个 ESP32」的事实。链路安全靠 `TUNNEL_TOKEN`。

### 9.4 真机验收结果

| 场景 | 结果 |
|---|---|
| 冷启动 → 连上 → hello 登记 | 3~5 秒 |
| 连续 30 次抓取（5 个站点轮换） | **30/30**，单次 206~3625ms |
| 串口未打开状态下 10 次调用 | **10/10**（这是修复前必挂的场景） |
| 空闲 100 秒后再调用 | **4/4**，连接未掉 |
| 冷启动干净批次 12 次 | **12/12**，面板成功率 100%，平均 478ms |
| 200 秒纯空闲不发调用 | 连接稳定不掉线 |
| `v.douyin.com` 抓取 | **成功**，拿到分享页骨架 `<script>var glb;...` |

### 9.5 这一轮真正花时间的四个问题

| 现象 | 根因 | 修法 |
|---|---|---|
| 板子无限重启 | `build.flash_size` 硬编码 4MB | 显式覆盖为 8MB |
| **调用必超时 20s，随后设备「离线」** | `Serial.printf` 在 TX 环形缓冲满时**阻塞**；主机不在读串口时（生产状态）长日志会卡住 `loop()`，心跳停摆 | 换成带 `Serial.availableForWrite()` 余量检查的 `logf()`，余量不足就丢这条日志 |
| 调用卡满 20s 才回 timeout | TCP 半开：`readyState` 仍是 OPEN，`send()` 也成功，但数据石沉大海 | Relay 记录设备最后出声时间（存在 attachment 里，能扛 DO 休眠），超 30s 回 503 `esp32_stale` |
| 设备明明活着却一路 503 offline | 旧连接的 `close` 事件晚于新连接建立才到，把新连接的引用清掉了 | `if (t.esp32 === ws) t.esp32 = null`，只清自己那条 |

另外顺手修的两个：

- **路由器 DNS 会丢查询、还被运营商改写**：`v.douyin.com` 在 192.168.1.1 上连超两轮才回，回的是 `v.douyin.com.queniuiq.com`（ISP 改写域名），阿里 DNS 给的是真地址。核心里的 `hostByName` 没有超时参数，DNS 一卡就把 `loop()` 堵死 → 固件里把 DNS 固定成 `223.5.5.5 / 119.29.29.29`。
- **预览代理把 POST 降级成 GET**：`fetch(url)` 默认 GET，面板命令台的 `POST /admin/api/call` 到 Manager 一律 404。`lan-gateway.mjs` 与 `panel-preview.mjs` 都改成原样转发 method + body。

### 9.6 已知限制（诚实记录）

- **`capacity = 1`**：主循环单线程，一次 fetch 期间新 CALL 只能排队。报成 2 是在把「排队」伪装成「并发」。
- **半开检测窗口最长 30 秒**：心跳 20s 一次，阈值 30s。这段时间内下发的调用仍会等满超时。要缩短得把心跳降到 10s。
- **单次抓取上限 128KB / 总预算 15s**：都在固件里写死，可用 args 微调但有上限。
- **真机到 Cloudflare 的 wss 路径未验证**：这一轮全部走本地明文 `ws://`（`TEST_MODE=1`）。上生产要改回 `TEST_MODE=0` 并重新烧录。
  → **已于 2026-10-25 补验，见 §10。**

## 10. 生产部署实测（2026-10-25）

### 10.1 部署形态

| 项 | 值 |
|---|---|
| Worker 名 | `esp32-exit`（**独立于 v3 的 `esp32-wol-tunnel`**） |
| 域名 | `exit.example.com`（custom domain，自动建 DNS） |
| 体积 | 81.81 KiB / gzip 24.89 KiB |
| 配置文件 | `worker/wrangler.exit.toml` |
| 部署命令 | `wrangler deploy --config wrangler.exit.toml` |

**为什么要单独一个 Worker 而不是复用 v3**：v3 的 `tunnel.example.com` 跑着家里 D0WD 板子的
定时唤醒链路。新代码是 fail-closed 鉴权，v3 的老固件不带 token，一次 `wrangler deploy`
就会把它打死。两个配置文件 → 两个独立 Worker → 两套独立 DO → 互不影响。

### 10.4 这把令牌现在在哪

`TUNNEL_TOKEN` 明文写在固件 `ESP32_C6_Exit.ino` 的生产分支里。这是嵌入式绕不开的：
板子要能证明「我是那台板子」，就得有一个它自己知道的秘密，而 flash 是可读的。

缓解措施：

- 面板上能一眼看到「设备密钥 已启用」，不用猜
- 轮换流程 = 改 secret + 改固件一行 + 重烧，十分钟的事
- 即使被读出，攻击者也只能**冒充你的板子接入**，拿不到任何已抓数据（数据不落盘）

`ADMIN_TOKEN` 和 `CLIENT_KEYS` 只在 Cloudflare secret 里，代码和固件都没有。
