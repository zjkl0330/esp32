# 02 · 对外通道与安全

这份文档回答三件事：**外面的请求怎么进来**、**谁能进来**、**进来以后能干什么**。

---

## 1. 一句话总览

```
其他项目 ──HTTPS──> exit.example.com ──WS──> ESP32-C6（你家）──TLS──> 目标网站
                    （Worker，公网）        （板子，出站连接）
```

板子**主动往外连**，所以你家路由器不需要端口映射、不需要公网 IP。这也是整个方案能成立的根本原因。

代价是：**板子不能当通用代理**。它只做「把这个 URL 的响应体搬回来」这一件事，因为
C6 单核 320KB 堆扛不住多路 TCP 中转（`cloudflare:sockets` 的 `startTls()` 又不能作用于
WS 消息流，TLS 只能在板子上终结）。

---

## 2. 三层钥匙

这是安全模型的核心。**三种用途、三把钥匙、互不通用**。

| 层 | 环境变量 | 谁持有 | 干什么 | 泄漏后果 |
|---|---|---|---|---|
| 设备层 | `TUNNEL_TOKEN` | 板子固件 + Worker | 板子连上来时证明「我是那台板子」 | 别人能冒充你的板子接入（但拿不到任何数据） |
| 管理层 | `ADMIN_TOKEN` | 只有你 | 打开面板、看状态、手动下命令 | 别人能看你的节点状态、用你的出口 |
| 应用层 | `CLIENT_KEYS` | 每个项目一把 | 调 `/api/fetch` 抓网页 | **只影响那一把**，撤掉重启即可 |

为什么应用层必须是**多把**而不是一把：一把 key 发给两个项目，泄漏了你不知道是谁漏的，
只能全撤、全停。多把才能做到「停一个、其余照跑」。

`CLIENT_KEYS` 格式（JSON 数组，放在 secret 里）：

```json
[
  { "name": "rin",   "key": "sk_rin_xxxxxxxx",   "dayCalls": 2000, "dayBytes": 52428800 },
  { "name": "clist", "key": "sk_clist_xxxxxxxx", "dayCalls": 500,  "dayBytes": 10485760,
    "hosts": ["*.githubusercontent.com"] }
]
```

| 字段 | 含义 |
|---|---|
| `name` | 显示名，同时是配额计数的键，必须唯一 |
| `key` | 32 字节以上随机串 |
| `dayCalls` | 每日调用上限，不填 = 不限 |
| `dayBytes` | 每日回传字节上限，不填 = 不限 |
| `hosts` | 域名白名单，支持 `*.example.com`，不填 = 除私网外全放行 |

**日界按北京时间切**，因为给你自己看的数字要跟你的直觉一致。

## 3. fail-closed：没配就等于拒绝

这是这轮改动里最重要的一条设计决定。

旧代码是：

```ts
if (!want) return true;   // 没配口令 = 不鉴权
```

看着像「本地开发方便」，实际是**安全生产事故的标准模板**：本地为了省事没配，
部署时忘了加，线上就一直敞着，而且没有任何报错提示你敞着。

现在改成：

- 没配 `ADMIN_TOKEN` → 面板返回 503 + 一页「缺哪一项、用什么命令补」
- 没配 `TUNNEL_TOKEN` → 所有设备通道 503
- 没配 `CLIENT_KEYS` → `/api/fetch` 503

宁可自己一时打不开，也不要让任何人能拿你家的网络当出口。

## 4. 对外抓取 API

### 4.1 基本用法

```bash
# 直接拿网页字节（适合 curl / 下载）
curl -H "Authorization: Bearer sk_rin_xxxx" \
     "https://exit.example.com/api/fetch?url=https://www.baidu.com" \
     -o page.html

# 拿结构化结果（带状态码、耗时、字节数）
curl -H "Authorization: Bearer sk_rin_xxxx" \
     "https://exit.example.com/api/fetch?url=https://www.baidu.com&json=1"

# 查今天还剩多少额度
curl -H "Authorization: Bearer sk_rin_xxxx" \
     "https://exit.example.com/api/me"
```

响应头里带元信息，不用解析 body 就能知道发生了什么：

| 响应头 | 含义 |
|---|---|
| `x-exit-ms` | 从下发到拿完的总耗时（毫秒） |
| `x-exit-bytes` | 回传字节数 |
| `x-exit-key` | 是哪把 key 发起的 |
| `x-exit-redirects` | 跟了几次跳转 |

### 4.2 从代码里调

```js
// Node / 浏览器（浏览器里别放 key，见 §6）
const r = await fetch('https://exit.example.com/api/fetch', {
  method: 'POST',
  headers: {
    'authorization': 'Bearer sk_rin_xxxx',
    'content-type': 'application/json',
  },
  body: JSON.stringify({ url: 'https://v.douyin.com/xxxx/', maxBytes: 65536 }),
});
const html = await r.text();
```

```python
import requests
r = requests.post(
    'https://exit.example.com/api/fetch',
    headers={'authorization': 'Bearer sk_rin_xxxx'},
    json={'url': 'https://v.douyin.com/xxxx/', 'maxBytes': 65536},
    timeout=30,
)
print(r.status_code, len(r.content))
```

### 4.3 错误码

| 状态 | `error` | 含义 |
|---|---|---|
| 401 | `unauthorized` | key 不对，或者没带 |
| 403 | `target_blocked` | 目标是私网/回环/元数据地址，被 SSRF 防护拦了 |
| 403 | `host_not_allowed` | 该 key 配了白名单，但目标不在名单里 |
| 429 | `quota_calls` | 今天的调用次数用完了 |
| 429 | `quota_bytes` | 今天的流量额度用完了 |
| 503 | `no_available_node` | 板子不在线 |
| 503 | `esp32_stale` | 板子的连接是半死的（socket 开着但没响应），直接失败不白等 |
| 502 | `fetch_failed` | 板子去取的时候失败了（DNS、TLS、超时） |

**所有失败都是显式的**，没有「假装成功」。这是刻意的：静默失败会在下游变成更难查的问题。

## 5. SSRF 防护：为什么必须做

这个 Worker 的 fetch 最终由**你家局域网里的板子**发出。也就是说板子的网络位置
比 Worker 本身更靠近你的路由器。如果放任它去取 `http://192.168.1.1`，
任何拿到 key 的人就获得了**内网探测能力**——包括你的路由器管理页、NAS、
以及云环境的元数据服务（`169.254.169.254`，SSRF 最经典的攻击目标）。

现在拦这些东西：

```
127.0.0.1        回环
127.x.x.x        整个回环段
10.x.x.x         私网
172.16-31.x.x    私网
192.168.x.x      你自己的局域网
169.254.x.x      链路本地 + 云元数据
100.64-127.x.x   运营商 CGNAT 大内网
0.x.x.x          全零段
::1 / fd00:: / fe80::   IPv6 回环与私网
localhost / *.local / *.internal / *.home.arpa   mDNS 能直达你家设备
2130706433       十进制的 127.0.0.1
0x7f000001       十六进制的 127.0.0.1
```

最后两种最容易漏。`http://2130706433/` 在很多解析器里就等于 `127.0.0.1`，
只判「字符串里有没有点」的写法会直接放行。

这些规则有 **19 条自动化用例**（`node test/security.mjs`）盯着，改坏了会立刻红。

### 还拦不住的一种

域名解析到内网 IP 的情况，Worker 侧看不到解析结果。这一层要在固件里补：
板子拿到 IP 后再判一次私网，命中就拒绝。**两层都要做，因为两层看到的信息不同。**

## 6. 已知风险（诚实列出）

| 风险 | 现状 | 为什么可接受 / 怎么缓解 |
|---|---|---|
| `TUNNEL_TOKEN` 存在固件 flash 里 | 能被物理读出 | 嵌入式没法像浏览器那样存密钥。缓解：token 可随时轮换，换完重烧固件 |
| 板子不验证目标网站证书（`setInsecure()`） | 存在中间人可能 | C6 上没有证书包。缓解：只取公开网页，不放任何凭据进请求 |
| TLS 指纹是 mbedtls，不是浏览器 | 目标站可能识别出来 | 无解，除非换硬件。这也是 M4 抖音解析的风险之一 |
| 单节点 = 单点故障 | 板子掉线就全停 | 面板会明确显示「连不上了」，不会假装正常 |
| Worker 免费版每天 10 万请求 | 够用但会撞墙 | 配额本身就是第一道闸，正常家用远达不到 |
| key 放在浏览器前端 | 任何人都能扒出来 | **不要这么做**。浏览器端项目走后端转发，key 只存在服务端 |

## 7. 部署

### 7.1 一次性配置

```bash
cd F:/esp32/tunnel/worker

# 三把钥匙（生成用 openssl rand -hex 24）
npx wrangler secret put TUNNEL_TOKEN --config wrangler.exit.toml
npx wrangler secret put ADMIN_TOKEN  --config wrangler.exit.toml
npx wrangler secret put CLIENT_KEYS  --config wrangler.exit.toml
```

### 7.2 部署

```bash
# 项目根目录双击，或命令行
F:/esp32/tunnel/deploy-exit.bat
```

等于：

```bash
cd F:/esp32/tunnel/worker
npx tsc --noEmit                                    # 门禁：类型不过不部署
npx wrangler deploy --config wrangler.exit.toml
```

### 7.3 验证

```bash
curl https://exit.example.com/health             # {"ok":true}
curl -o /dev/null -w "%{http_code}" https://exit.example.com/admin   # 401（没带口令）
curl -H "Authorization: Bearer <ADMIN_TOKEN>" -o /dev/null -w "%{http_code}" \
     https://exit.example.com/admin              # 200
```

### ⚠️ 不要用 `wrangler deploy`（不带 --config）

那个命令会用 `wrangler.toml`，部署到 **v3 生产隧道 `tunnel.example.com`**。
新代码是 fail-closed 鉴权，v3 的老固件不带 token，一部署就把家里的唤醒链路打死。

## 8. 固件侧需要对应的改动

生产模式（`TEST_MODE 0`）下：

```cpp
const char* WS_HOST = "exit.example.com";
const uint16_t WS_PORT = 443;
// token 走 Authorization 头。不要拼进 URL —— URL 会落进 CF 边缘日志和
// 中间代理的访问记录，Worker 侧也已经不再接受 ?token=（见第 10 节）。
webSocket.setExtraHeaders("Authorization: Bearer <TUNNEL_TOKEN>");
webSocket.beginSslWithCA(WS_HOST, WS_PORT, "/ws/exit/esp32", ROOT_CA);  // 根证书见第 10 节
```

隧道名从 `wol` 改成 `exit`：这是新 Worker 的独立隧道，跟 v3 那条完全不交叉。

## 10. 公网能被抓包吗（2026-10-25 评估与修复）

### 被动监听：看不到内容

| 环节 | 加密 | 中间人能看到 |
|---|---|---|
| 设备 → CF | wss（TLS） | 目标 IP、**SNI 明文**（`exit.example.com`）、包大小、时序 |
| 浏览器 → 面板 | HTTPS | 同上 |
| 抓来的网页内容 | 在 TLS 里 | 看不到 |

没开 ECH，所以"你在连哪个域名"是可被观察的；但 token、URL 路径、抓到的内容都在 TLS 内。
运营商级中间盒除非装了私有 CA 并能让客户端信任，否则解不开。

### 主动劫持：原来能做到，因为设备不校验证书

这是本次查出来的真问题，不是推测：

```cpp
// 修复前的固件
webSocket.beginSSL(WS_HOST, WS_PORT, WS_PATH);
```

`WebSocketsClient::beginSSL` 三参数版既不传 CA 也不传 fingerprint，
库内部直接走（`WebSocketsClient.cpp:295`）：

```cpp
} else if(!SSL_FINGERPRINT_IS_SET) {
    _client.ssl->setInsecure();      // 不验证对端是谁
```

后果链：

1. 攻击者出示自签证书冒充 `exit.example.com`，设备照连 → 握手头里的
   `Authorization: Bearer <TUNNEL_TOKEN>` 被收走
2. 用这个 token 冒充这台设备连 Worker（吃你家的额度和 IP）
3. **更严重：绕过 SSRF 防护**。禁内网的检查在 Worker 的 `checkTarget()` 里，
   设备自己不判目标。TLS 一破，攻击者不用碰 Worker，直接冒充它下发
   `https_fetch host=192.168.1.1`，设备就会去抓自家路由器管理页并回传。
   也就是说「证书不校验」把内网隔离整个作废了

能做这件事的人：同一 WiFi 下的设备（需 WiFi 密码或 ARP 欺骗能力）、
被控的路由器、上游中间盒。家里 WiFi 有密码时门槛不低，但设备一旦挪到
学校/公共网络就是敞开的。

### 修复

固件改用 `beginSslWithCA`，并先对时：

```cpp
// 1. WiFi 连上后先 NTP 对时（C6 没 RTC，开机是 1970，证书有效期判断必失败）
[ntp] 已对时 2026-10-25 13:44:54（3199ms）
// 2. 用根证书发起 wss
[WS] connected heap=275396 largest=249844
```

根证书选的是 **GTS Root R4 + ISRG Root X1**：

```
example.com ← WE1 ← GTS Root R4 ← GlobalSign Root CA
```

CF 现在用 Google Trust Services 的 WE1 签发，根是 GTS Root R4；再带一张
ISRG Root X1 兜底 CF 换回 Let's Encrypt 的情况。两张都是自签根，
有效期到 2036 / 2035，**不会跟着服务器证书 90 天轮换而失效**，不需要重烧。

### 反向验证（关键：证明防护真在跑）

"设备能连上"这件事，在"校验通过"和"根本不校验"两种情况下都成立，
所以它不能作为证据。于是做了一次证伪：把根证书临时换成**不匹配**的
ISRG Root X1（不含 GTS Root R4），重烧后观察：

| 固件 | 串口表现 |
|---|---|
| 只有不匹配的根 | 反复 `[WS] DISCONNECTED`，**零次** `[WS] connected`、**零次** `[hello]` |
| 正确两个根 | `[WS] connected` + `[hello]` 正常 |

这才叫确认。如果它还在 `setInsecure`，第二种和第一种没区别。

### 顺带修掉的：口令不再走 URL

| 项目 | 原来 | 现在 |
|---|---|---|
| 面板登录 | `GET /admin?token=xxx`（进 CF 日志、浏览器历史、密码管理器） | `POST /admin/login`，body 里带口令，换成 HttpOnly 会话 Cookie |
| 设备鉴权 | Bearer / `?token=` / 子协议 三选一 | 只认 Bearer 和子协议 |
| 旧链接 | —— | 401 并提示"口令不能再放在网址里" |

`Relay.ts` 里的 query token **故意保留**：v3 的 `tunnel.example.com` 手机唤醒页
靠它工作，exit 侧已经被 `index.ts` 的 Bearer-only 挡在前面了。改它会打断现有链路。

### 再往后：用户名 + 口令，密钥表搬进 DO（2026-10-25 晚）

| 变化 | 说明 |
|---|---|
| 登录改成用户名 + 口令 | 用户名 `ADMIN_USER`（默认 `admin`），口令 `ADMIN_TOKEN`。两者都参与会话派生（HMAC(user + 口令)），所以换用户名会让所有旧会话立刻失效 |
| 脚本鉴权不受影响 | `Authorization: Bearer <口令>` 照旧可用（脚本不用带用户名）；也接受 `Bearer <用户名>:<口令>` |
| 接出密钥表从 secret 搬到 DO | secret 是只写不可读的，面板要能「显示密钥 / 新增 / 吊销」就必须有个可读可写的地方。现在密钥表存在 Manager DO 的 storage 里，`CLIENT_KEYS` secret 只在第一次当种子用 |

**为什么密钥明文落进 DO 存储是可以接受的**：面板本来就要显示它，
`ADMIN_TOKEN` 等同于「能通过你家设备访问内网」的权限（管理路径不拦内网地址），
能进面板的人本来就能拿到这些密钥。真正要防的是**外部拿到 key**，
所以每把 key 独立配额、独立吊销，一把出事只停一把。

**风险提醒**：`ADMIN_TOKEN` 现在是弱口令，而服务在公网上。
它同时是「看面板」「管密钥」「让设备抓内网」三件事的总钥匙 ——
一旦被爆破拿到，等于你家内网对攻击者开放。建议至少换成一个长随机串。

### 仍然存在的边界

- **Cloudflare 能看明文**。这是信任边界，绕不过去；不接受就只能自建服务器。
- **设备 flash 里的 TUNNEL_TOKEN 是明文**，物理接触可读。
- 想连 Cloudflare 都不信任，就得在 WS 之上再加一层 AEAD（XChaCha20-Poly1305），
  让内容即使 TLS 被破也读不了、改不了。目前没做，因为现在传的是公开网页内容，
  收益不够。
- SNI 明文可见（未开 ECH）。
