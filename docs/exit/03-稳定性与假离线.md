# 03 · 稳定性压测与假离线根因

> 2026-10-25 首次稳定性压测。目的不是"证明它能用"（`prod-verify` 已经做过了），
> 而是回答三个问题：**会不会漏内存 / 边界输入会不会打挂 / 设备是不是偷偷掉线**。

## 一、方法：为什么这么做

**不开串口。** 生产环境没人读串口。固件的 `logf()` 在 `availableForWrite()` 余量不足时直接丢日志，
开了串口就等于改变了被测对象的行为，测出来的不是生产条件。全程只走 HTTP 观测。

**泄漏要静置对比，不能算斜率。** 抓取瞬间 TLS 上下文要吃 20~25KB，
采样点落在"正在抓"还是"闲着"上，差值比泄漏量本身大十倍。第一版脚本拿压测过程中的
heap 序列算线性回归，跑出过 `+28291 B/分钟` 这种纯噪声。正确做法是两次静置取样：

```
压测前静置 45s（等两轮心跳刷新）→ 采 3 次取中位
        ↓ 打 130 次调用
压测后静置 45s → 再采 3 次取中位
差值 ÷ 调用次数 = 每次净变化
```

## 二、结果

### 边界场景

| 场景 | 结果 | 说明 |
|---|---|---|
| 基线小文件 ×10 | 10/10，均 772ms | 正常 |
| 撞体积上限 ×3（QQ 首页） | 3/3，单次 123KB | 没崩，但**没有 truncated 标记**（见遗留项 1） |
| 明文 HTTP + 跳转 ×3 | 3/3，单次 131KB | 302 跟随正常 |
| 域名不存在 ×2 | 0/2，均 6.6s | 报错正确但**偏慢**（见遗留项 2） |
| 黑洞 IP 192.0.2.1 ×2 | 0/2，均 8.5s | 给了 8s 预算就花 8.5s，没超全局 15s |
| DNS 工具 ×5 | 5/5，均 449ms | 正常 |
| net_info ×5 | 5/5，均 453ms | 正常 |

### 连续负载 100 次（间隔 250ms）

- 成功 100/100，均 891ms，总流量 790KB
- 压测期间 heap 在 274664 ~ 251496 之间波动，幅度 23KB = TLS 上下文的瞬时占用
- **静置对比：274664 → 274640，130 次调用净 -24B（每次 -0.2B）→ 无泄漏**

### 并发

五路同时下发，全部 200，各自 213~265ms，墙钟总 2182ms —— 设备单线程串行处理，
请求会排队而不是失败。家用出口这个行为是对的（`capacity=1` 不是缺陷，是实情）。

## 三、假离线：这次压测最值钱的发现

### 症状

压测开局 `snapshot` 报 `online=false · 静默788s`，但紧接着 130 次调用全部成功，
设备自报的连接 `up` 还在连续增长。手工复现三次，拿到 `false / true / false`：

```
12:30:12  online=false  silent=1359s  up=undefined
12:31:44  online=true   silent=5s     up=1446
12:33:15  online=false  silent=1542s  up=undefined
```

`1359` 和 `1542` 都精确指向设备 `hello` 的那一刻（2026-10-25 12:07:33）。

### 根因

`Manager` 的 `persist()` 只在 `/hello` 时调用，`/hb` 的注释明确写着「只更内存 + 序列，不落盘」。
而 **Durable Object 空闲十几秒就会被回收**，设备心跳 20s 一次，正好卡在驱逐边缘：

```
hello → 落盘 lastSeen=12:07:33
  ↓ 每 20s 心跳，只更新内存
DO 被回收
  ↓ 下一个请求唤醒它
从 storage 恢复 → lastSeen 退回 12:07:33 → now - lastSeen 远超 50s TTL → 判离线
```

后果不是"面板数字难看"，是 `/api/fetch` 会真的返回 `503 no_available_node`——
家里板子活得好好的，外面调不通。

### 修复

1. **心跳落盘**（`/hb` 里 `await this.persist()`）：一天 4320 次写，DO 配额上是九牛一毛，
   换"不再假离线"怎么算都值。原注释判断"一天几千次写纯属白烧额度"是错的。
2. **恢复宽限 30s**：DO 重建时若恢复出的 `lastSeen` 已过期，给一个宽限期等下一轮心跳，
   不立刻判死。真死了还有 Relay 的 `esp32_stale` 兜着，不会让人白等 20s。
3. **今日统计持久化**：`stats` 独立落盘，不再从内存里的 `tasks` 数组数。
   原来 DO 一回收，面板上「今日 N 件」就归零。

### 验证

| 检查 | 修复前 | 修复后 |
|---|---|---|
| 静置 90s 后单次采样 | `silent=1359s` | `silent=4s` |
| 今日统计跨驱逐 | 3 → 0 | 3 → 3 |

- `test/manager-evict.mjs` 13/13（用同一个 storage 起两个 Manager 实例模拟驱逐重建）
- `test/prod-revive.mjs` 线上验收全绿

> 写测试时踩到一个坑：`FakeStorage` 如果直接存对象引用，测出来的是假绿。
> 真实的 `DurableObjectStorage` 是结构化克隆语义，存进去和取出来不是同一个对象。
> 必须 `structuredClone`，否则心跳更新的字段会"偷偷"出现在已落盘的数据里。

## 四、遗留项

1. **静默截断没有标记**。固件 `sendResult()` 的 meta 里没有 `truncated` 字段，
   抓取撞到 128KB 上限时，成功路径完全不给上层任何提示 —— 调用方会把半截内容当完整的用。
   修法很小（meta 加一个字段，两处调用点传 `r.truncated`），但要重烧固件，
   等下次烧录时一起处理。
2. **DNS 失败要 6.6s 才报错**。理想应在 1s 内返回。目前不影响正确性，只是浪费预算。

## 五、怎么跑

```bash
cd F:/esp32/tunnel
ADMIN_TOKEN=xxx node test/soak.mjs all          # 场景 + 负载，约 6 分钟
ADMIN_TOKEN=xxx node test/soak.mjs watch 600    # 只被动观察 10 分钟
ADMIN_TOKEN=xxx node test/prod-revive.mjs       # 部署后验收假离线，约 5 分钟
node test/manager-evict.mjs                     # 驱逐逻辑单测，秒级
```

原始数据落在 `test/.soak/run-*.jsonl`，每次调用一行。
