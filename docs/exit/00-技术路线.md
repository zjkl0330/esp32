# ESP32-C6 住宅出口 + Workers 控制面：技术路线（调研结论）

> 生成日期：2026-10-25
> 状态：**调研 + 选型稿**。所有"可编译/可运行"结论均经本地核实，未经核实的明确标注。
> 前置文档：资料库 `management-plane`（Manager DO + Relay DO 双面设计）。

---

## 0. 三条结论（先看这个）

1. **原方案的核心假设已经不成立一半。**
   抖音对公开接口（`iteminfo`、分享页 SSR 的 `#RENDER_DATA` / `_ROUTER_DATA`）已加 `a_bogus` / `msToken` 签名 + Cookie 校验，纯静态请求会拿到风控页。`iesdouyin.com/share/video/{id}` 的 `_ROUTER_DATA` 里 `loaderData["video_(id)/page"].videoInfoRes` 已被移除。
   **住宅 IP 是必要条件，不是充分条件。** 架构必须留出"Worker 侧可随时换解析策略"的位置。

2. **ESP32-C6 N8 不是升级，是横向替换。**
   Flash 4MB→8MB 是真收益（OTA 槽 1.2MB→3.34MB，现固件 1.197MB 占 91% 会降到 34%）；
   但 CPU 双核 240MHz→**单核 160MHz**、无 PSRAM。所以 C6 只能当**哑管道**，绝不能把解析逻辑焊进固件。

3. **GitHub 上没有"ESP32 住宅出口 + Workers 面板"的整套现成方案**，但有 8 个高质量零件可拆。面板部分建议**借骨架、自己写 UI**，硬套现成平台会别扭（数据流范式不同）。

## 2. 架构路线对比（含一条被排除的）

### 2.1 三条候选

| | A. 应用层抓取 | **A′. 通用 HTTPS 出口代理（推荐）** | B. Worker 接管 TLS |
|---|---|---|---|
| 谁建到目标的 TLS | ESP32 | ESP32 | Worker |
| 谁解析响应 | 固件 | **Worker** | Worker |
| 抖音改版怎么办 | **重烧固件** | 改 Worker 部署 | 改 Worker |
| ESP32 内存/连接 | 45KB/连接 + 页面缓冲 | 45KB/连接，流式不缓存 | 0（不可行） |
| 支持站点 | 只有焊死的几个 | **任意域名/路径/Header** | — |
| 可行性 | 可行但僵 | **可行** | **❌ 不可行** |

### 2.2 为什么排除 B

B 看起来最优雅（ESP32 只搬字节、TLS 交给 Worker 的 BoringSSL），但有个硬阻断：

`cloudflare:sockets` 的 `startTls()` 只能作用于 `connect()` **返回的本地 socket 对象**。Worker 从 WebSocket 拿到的是**消息流**，拿不到可 `startTls` 的句柄。想在 Worker 侧对一条 WS 字节流做 TLS，等于自己实现 TLS 状态机——不现实。

**推论（重要）：TLS 一定跑在 ESP32 上，指纹就一定是 mbedtls。** 这是这套硬件方案的生理极限，任何"换个姿势就能伪装浏览器指纹"的说法都是假的。

### 2.3 A′ 的具体形态

```
浏览器 → POST /api/parse
   ↓
Manager DO ── 建任务 {id, tool:"https_fetch", args:{host, port, req}}
   ↓ (任务队列 + 长轮询)
ESP32 (C6) ─ WiFiClientSecure 建到目标 :443，写原始 HTTP 请求字节，流式回传
   ↓
Worker 收字节 → 解析（解析器在 Worker，随时可换）
   ↓
浏览器拿到 JSON
```

**ESP32 侧只认 4 个字：`host / port / bytes`。** 它不知道这是抖音还是别的。

### 2.4 能力上限（按 C6 实测算）

| 项 | 数值 | 来源 |
|---|---|---|
| C6 SRAM | 512 KB（可用 heap 约 320–400 KB） | 芯片参数 |
| 单条 TLS 握手 | ~45 KB | 你在经典 ESP32 上的实测（213392→168100） |
| 常驻 WS 到 Worker | 1 条 × 45 KB | 必须 |
| 可并发目标连接 | **2 稳，3 上限** | 45×3 + 45 + 栈余量 |
| TCP PCB 预算 | 6 | lwIP 默认 `MEMP_NUM_TCP_PCB=16`，C6 实测预算 6 |

→ 管理面文档里 `capacity: 3~5` 要**改成 2~3**（C6）。这是硬件决定，不是保守。

## 3. 设备核实：ESP32-C6 N8

| 项 | ESP32-D0WD（现有） | ESP32-C6 N8（拟用） | 判断 |
|---|---|---|---|
| Flash | 4 MB | **8 MB** | ✅ OTA 槽 1.2MB → 3.34MB |
| 核心 | Xtensa **双核** 240MHz | RISC-V **单核** 160MHz | ⚠️ 变弱 |
| SRAM | 520 KB | 512 KB | ≈ 持平 |
| PSRAM | 无 | 无 | 一样受限 |
| Wi-Fi | 802.11 b/g/n | **802.11ax (Wi-Fi 6)** | ✅ 弱信号更稳 |
| 802.15.4/Thread | 无 | 有 | 用不上 |
| Flash 下载口 | CP210x（COM3） | 原生 USB Serial/JTAG | ⚠️ 首次烧录注意 `USB CDC On Boot` |

**本地已核实（真实读文件，非推测）：**

- `arduino-cli` 的 esp32 core **3.3.10-cn** 里存在 `esp32c6.name=ESP32C6 Dev Module`，`esp32c6.build.mcu=esp32c6`。
  → FQBN = `esp32:esp32:esp32c6`
- 分区表实测内容 `tools/partitions/default_8MB.csv`：
  ```
  nvs      0x9000   0x5000
  otadata  0xe000   0x2000
  app0     ota_0    0x10000   0x330000   ← 3.34 MB
  app1     ota_1    0x340000  0x330000   ← 3.34 MB
  spiffs   0x670000 0x180000
  coredump 0x7F0000 0x10000
  ```
  → **双 OTA 槽确实存在**，必须显式指定 `PartitionScheme=default_8MB`；若用默认 `default`（4MB 方案）会浪费 4MB flash。

**诚实结论：** C6 适合"纯出口"这一个角色。别把经典 ESP32 退役——它双核 + 240MHz，如果哪天要做"端侧解析"或"多并发抓取"，反而比 C6 强。留着当第二个出口节点（正好接上多节点分流设计）。

## 4. 协议设计：设备工具表（"预加载工具"的落地）

**理解说明**：把"预加载工具"落成**设备端工具表（tool registry）**——固件编译进固定工具集，Worker 按 `{op, tool, args}` 下发，设备执行回传。这样加工具只改固件，加业务只改 Worker。

### 4.1 帧格式（在现有 5 帧基础上扩展）

现有：`OPEN 0x01 / OPEN_OK 0x02 / DATA 0x03 / CLOSE 0x04 / WOL 0x05`（**保持不变，别动**）

新增：
```
CALL  0x06   Worker → 设备   {id, tool, args}
RESULT 0x07  设备 → Worker   {id, ok, meta, len}
（结果体走 DATA 帧，分块，8KB/块）
```

### 4.2 工具清单

| 工具 | 作用 | 成本 | 优先级 |
|---|---|---|---|
| `https_fetch` | 建 TLS 到 host:443，写原始 HTTP 请求，流式回传 | 中 | **P1** |
| `http_get` | 明文同款（内网站点/调试） | 低 | P1 |
| `net_info` | RSSI / IP / 网关 / DNS / heap / uptime / 重置原因 | 低 | **P1**（心跳合一） |
| `dns_lookup` | 域名解析，判断是否被污染 | 低 | P2 |
| `tcp_probe` | 端口连通性 + 延迟 | 低 | P2 |
| `wol` | 魔术包 | **已有** | — |
| `ota_apply` | 拉固件 → 写另一分区 → 重启 | 中 | **P2** |
| `reboot` / `config_get` / `config_set` | 运维 | 低 | P2 |

工具表写入 NVS，`/admin` 可读 → 实现**能力协商**（面板只显示设备支持的按钮）。

### 4.3 请求构造在哪一侧

**必须 Worker 侧拼**（`GET /path HTTP/1.1\r\nHost:...\r\nUser-Agent:...`），ESP32 只负责把这段字节写进 TLS 通道。原因：Header 顺序、UA、Cookie 都是反爬变量，改了要能立刻生效。

## 5. OTA 设计

### 5.1 流程图

```
设备心跳上报 version
   ↓
Worker 比对 manifest（KV/D1）
   ↓ 有新版
CALL {tool:"ota_apply", args:{url, sha256, size, version}}
   ↓
设备: HTTP 拉 R2 → 边下边写 Update.write() → sha256 校验
   ↓
SetBootPartition(另一槽) → NVS 写 pending_confirm → 重启
   ↓
新固件起来 → 30s 内无 panic + WS 重连成功 → 清除 pending_confirm
   ↓ 若 30s 内崩溃/未确认
bootloader 自动回滚上一槽
```

### 5.2 关键设计点

1. **固件二进制放 R2**，Worker 只发 URL。绝不让 Worker 转发 1MB+ 的 bin（CPU 时间 10ms/请求的限制会直接超）。
2. **manifest 字段**：`{hw:"esp32c6-n8", version, url, sha256, size, min_from, channel}`。`hw` 必须匹配，防止把经典 ESP32 的 bin 刷进 C6（**会砖**）。
3. **先落 pending 标记再重启**，不要在 OTA 下载线程里 reboot。
4. **双分区必须真验证**：故意推一个会 panic 的固件，确认自动回滚。这是抄 cabin-monitor 的做法——不验证回滚就等于没有回滚。
5. `default_8MB` 槽 3.34MB，现固件 1.197MB，余量大；但**别把 Web 前端打进固件**（LittleFS 只 1.5MB，且会挤 OTA 空间），面板全部放 Worker。

## 6. Workers 控制面板

### 6.1 路由

| 路由 | 内容 |
|---|---|
| `/admin` | 首页：节点卡片（在线/负载/heap/RSSI/固件版本）、今日请求数、告警 |
| `/admin/node/:id` | 详情：工具列表、实时日志、命令台（任选工具+参数直接调）、OTA 按钮 |
| `/admin/ota` | 版本管理：上传 bin → R2、编辑 manifest、灰度（指定 nodeId 升级） |
| `/admin/task` | 任务队列：待处理/执行中/失败重试，带原始请求与响应头 |

### 6.2 存储分工

| 组件 | 存什么 | 为什么 |
|---|---|---|
| Manager DO | 节点表、工具表缓存、任务队列、长轮询挂起 | 需要单实例强一致 |
| Relay DO（已有） | 每 tunnel 一条 WS 配对、字节转发 | 不动 |
| D1 | 审计日志、OTA 历史、请求统计 | 要分页查询 |
| KV | manifest、面板配置、token 哈希 | 读多写少 |
| R2 | 固件 bin | 10GB 免费 |

### 6.3 鉴权

单 token（`ADMIN_TOKEN` secret），面板登录后写 HttpOnly Cookie；设备侧用另一个 `DEVICE_TOKEN`，两者不共用。所有比较走常量时间（抄 stackchan 的做法）。

### 6.4 UI 参考

信息架构抄 Tasmota Dashboard（设备清单 → 详情抽屉 → 批量操作 → 审计），**但布局自己写**，别引它的依赖。视觉上用单页 + SSE（HelloESP 已证明 ESP32 侧 SSE 可行，且比轮询省）。

## 7. 分阶段实施与验收

### P0 — 沙箱可验证（不碰硬件，先证明协议对）

1. `worker/src/protocol.ts` 加 `CALL/RESULT` 帧编解码
2. `test/mock-esp32.mjs` 扩展：响应 `https_fetch`，从本地假 TLS 服务取字节
3. `test/e2e.mjs` 新增用例：Worker 下发 CALL → mock 回 3 块 DATA → 断言拼回的字节与原文件 sha256 一致

**门禁**：现有 **10/10 e2e 全绿不退** + 新增用例绿 + `tsc --noEmit` 0 error。

### P1 — C6 固件跑通

1. 新建 `arduino/ESP32_C6_Exit/`，FQBN `esp32:esp32:esp32c6` + `PartitionScheme=default_8MB`
2. 实现 `https_fetch` + `net_info`（心跳合并进 WS ping，省一条 HTTPS）
3. **串口验收（必须现场看日志）**：连上 Worker → 下发一次真实 https 请求 → 打印状态码 + 首 200 字节 + heap 余量

**门禁**：串口日志里能读到真实响应；`heap` 在单请求峰值后不低于 100KB。

### P2 — OTA

1. R2 bucket + manifest
2. `ota_apply` + `pending_confirm` + 回滚
3. **故意推坏固件验证回滚**（这一步不做完，OTA 不算交付）

### P3 — 面板

`/admin` 三个页面 + 命令台。验收：手机浏览器能看节点状态并成功调一个工具。

### P4 — 抖音（止损点在这里）

1. 把 `jiuhunwl/short_videos` 的 Workers 版解析逻辑搬进来
2. **A/B 实测**：同一分享链接，CF 出口 IP vs 家庭出口 IP，各打 10 次，记成功率
3. **止损规则**：试满 3 条路径（分享页 SSR、`iteminfo` 详情、直链 302）仍无稳定成功 → 停，把系统定位成"通用住宅 IP 出口"，抖音这条线挂起，不硬刚签名。

## 8. 风险与止损

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 抖音分享页已加 `a_bogus`/`msToken` | P4 可能做不成 | 设止损点（见 P4）；架构保证"换策略不改固件" |
| 2 | mbedtls TLS 指纹 ≠ 浏览器 | 可能直接判机器人 | **无解，只能换硬件**（旧安卓 Termux + curl-impersonate / 树莓派）。协议不变，换设备成本低——这是 A′ 的最大价值 |
| 3 | C6 单核 160MHz 跑 TLS 到 CF 的常驻连接 | 吞吐低、Wi-Fi 抖动时易掉 | 实测吞吐；必要时降 `WiFi.setSleep`、固定信道 |
| 4 | 免费版 Workers：同时 6 连接、100s 无数据切断 | 大视频下载会断 | 分块 + 断点续传；大文件不要走 Worker 中转 |
| 5 | **Brownout**（已实测过） | 下载时功耗上升，必掉压 | **必须独立供电**，别用笔记本 USB |
| 6 | 家庭 IP 被打上标记 | 影响全屋网络 | 严格限频（个人使用量级），不批量刷 |
| 7 | 把经典 ESP32 的 bin 刷进 C6 | 变砖 | manifest 强制校验 `hw` 字段 |
