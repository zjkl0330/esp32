# 04 · 把这个出口接给其他项目用

> 一句话：**让别的项目发出的某个 HTTPS 请求，改成从家里那条宽带出去。**
> 目标站看到的来源 IP 是 `203.0.113.7`（江西电信），不是 Cloudflare、也不是你云服务器的 IP。
>
> 想让目标站把你当成「一个普通中国家庭宽带用户」而不只是「换了出口 IP」，
> 看下面「**用这个出口伪造家庭住宅 IP**」——那里面直接给结论：目的达成到什么程度、唯一的短板是什么、撞上短板怎么改。

## 先说清楚它是什么、不是什么

这一步最容易搞错，写在前头。

| 你想干的事 | 这个出口能不能干 |
|---|---|
| 抓一个网页 / 调一个第三方 API，让对方看到家庭 IP | **能** |
| 让被云厂商 IP 段封掉的接口重新能用 | **能** |
| 隐藏你服务器的「入站」IP（别人访问你时看不到源站） | **不能**。那是 CDN / 反向代理的事，跟出站无关 |
| 当通用 HTTP 代理（浏览器填个地址就能翻墙） | **不能**。它不是 proxy，是「抓取器」：一次调用 = 设备替你发一次请求、把字节拿回来 |
| 传大文件、跑 WebSocket、长连接 | **不能**。设备是一次性连接，抓完就断 |

所以准确的用法是：**你代码里某个 `fetch(第三方URL)` 想换出口 IP，就改成走它。**
仅此一件事，别的都别指望。

## 实测证据（不是推断）

```
本机直连  https://ip.3322.net            → 203.0.113.7
通过出口  GET /api/fetch?url=ip.3322.net → 203.0.113.7
通过出口  https://www.cloudflare.com/cdn-cgi/trace → ip=203.0.113.7 loc=CN warp=off
```

目标站自己报告 `origin=203.0.113.7`（见 `httpbin.org/post` 的返回）。这是目标站视角，不是我们自说自话。

## 接入方式

### 方式 1：用 SDK（推荐，最省事）

把 `sdk/exit-fetch.mjs` 复制到你的项目里。单文件、零依赖，Node 18+ / Workers / Bun / Deno 都能用。

```js
import { createExit } from './sdk/exit-fetch.mjs';

const exit = createExit({ key: 'sk_项目专属key' });

// 和原生 fetch 一模一样，只是多绕一跳
const res  = await exit.fetch('https://api.example.com/data');
const data = await res.json();

// POST / 自定义 header / 请求体 都支持
const r2 = await exit.fetch('https://httpbin.org/post', {
  method: 'POST',
  headers: { 'content-type': 'application/json', referer: 'https://example.com/' },
  body: JSON.stringify({ n: 42 }),
});

// 查这把 key 今天还剩多少额度
await exit.me();
```

两个关键行为：

- **`res.status` 是目标站的真实状态码**。目标返 404，你拿到的就是 404，不会被伪装成 200。
- **出口自己出问题时会抛 `ExitError`**（401 鉴权失败 / 额度用完 / 设备离线 / 内网地址被拦），带 `.status` 和 `.body`，能区分「目标拒绝我」和「出口坏了」。

### 方式 2：直接 curl（调试用）

```bash
# GET
curl -H "Authorization: Bearer sk_xxx" \
  "https://exit.example.com/api/fetch?url=https%3A%2F%2Fip.3322.net"

# POST + JSON
curl -H "Authorization: Bearer sk_xxx" -H "content-type: application/json" \
  -d '{"url":"https://httpbin.org/post","method":"POST","headers":{"content-type":"application/json"},"body":"{\"n\":42}"}' \
  https://exit.example.com/api/fetch
```

### 方式 3：在 Cloudflare Worker 里调

同方式 2，Worker 原生就有 `fetch`，直接打 `/api/fetch` 即可。注意**不要在 Worker 里套 SDK 的 `new Response()`** 那层封装，直接用 raw 请求更省。

## 能力与限制

| 项 | 现状 |
|---|---|
| 方法 | GET / POST / PUT / DELETE / PATCH / HEAD |
| 自定义 header | 支持（`host` / `accept-encoding` / `connection` 由固件自己管，其余全透传） |
| 自定义 UA | **支持**，可以伪装成任意浏览器（很多站点认这个） |
| 请求体 | ≤ **16KB**（要塞进 ESP32 内存里拼请求） |
| 单次响应 | 默认 **128KB**，可传 `maxBytes` 最多到 256KB |
| 重定向 | 自动跟随，最多 3 跳 |
| 状态码 | 原样透传（404/500 就是 404/500） |
| content-type | 目标站的值会带回来（`x-exit-ctype` 头，SDK 会挂成标准的 `content-type`） |
| 截断 | 撞上限或读不完都会标 `x-exit-truncated: 1`，不会静默给你半截 |
| 并发 | **1**。设备单核单连接，第二个请求会排队等第一个 |
| 每日额度 | 每把 key 独立配置，默认 main = 2000 次 / 50MB |

### 速度：这是硬件的上限，不是代码的问题

实测（ESP32-C6，单核 160MHz，mbedtls 软件 TLS，无 AES 硬件加速）：

| 响应体积 | 耗时 | 折算 |
|---|---|---|
| 1KB | 1.1s | 固定开销约 1 秒（TLS 握手 + 路由 + 调度） |
| 10KB | 1.7s | ~6 KB/s |
| 50KB | 6.5s | ~8 KB/s |
| 100KB | 9.3~12s | ~10 KB/s |

所以：**抓 JSON / 小接口（<10KB）完全够用，1~2 秒；抓普通网页（20~60KB）要 2~6 秒；抓大文件就别想了。**

试过把 `delay(1)` 轮询改成 `delay(0)`、把 DATA 帧从 1KB 提到 4KB，合计提速约 30%，剩下的全是硬件限制。
换 TLS 实现（bearssl）大概还能再快两成，但那是另一个工程量的改造，暂不做。

> 顺带一个坑：抓取是**同步阻塞** `loop()` 的，一次大抓取能堵十几秒。
> 固件 2.1.0 起在读 body 的过程中每 2 秒发一次心跳，所以堵着的时候连接不会被判离线
> （`test/fetch-hb.mjs` 就是钉这一条的）。

### 两个必须知道的坑

1. **不支持 gzip**。请求强制 `Accept-Encoding: identity`。绝大多数站点会照办，
   但少数无视此头的站点会返回压缩字节，你解不开（表现为乱码）。
2. **设备→目标这一段不校验证书**。运营商或路由器理论上能篡改返回的内容。
   抓公开网页无所谓，抓任何带身份的东西之前必须先解决（见文末遗留）。

## 给一个新项目发 key

每把 key 独立配额、独立吊销。**不要多个项目共用一把**，出事只能整把停。

### 方式 1：在面板上点几下（推荐）

登录面板 → 往下滚到「接出密钥」→ 点「+ 新增一把」→ 填名字、每日次数、每日 KB、
域名白名单（留空 = 不限）→ 点「创建」。

密钥会**立刻生成并生效**，不用改配置、不用重新部署。面板上「显示密钥」能看到明文，
「复制」直接拿走。出了事点「吊销」，那个项目立刻开始 401，其余项目不受影响。

### 方式 2：改 secret（批量初始化 / 灾备用）

密钥表平时存在 Durable Object 里，`CLIENT_KEYS` 这个 secret 只在**第一次**当种子用
（DO 存储被清空时会自动回落到 secret 的内容，不会变成一把都没了）。

所以如果你要一次性铺一批 key，可以把数组写进 secret：

```json
[
  { "name": "main",  "key": "sk_main_xxx",  "dayCalls": 2000, "dayBytes": 52428800 },
  { "name": "test",  "key": "sk_test_xxx",  "dayCalls": 100,  "dayBytes": 5242880 },
  { "name": "news",  "key": "sk_news_xxx",  "dayCalls": 300,  "dayBytes": 10485760,
    "hosts": ["*.example.com", "api.foo.cn"] }
]
```

```bash
cd F:/esp32/tunnel/worker
node ./node_modules/wrangler/bin/wrangler.js secret put CLIENT_KEYS --config wrangler.exit.toml
```

⚠️ 注意：**secret 里的内容只在面板里还没有任何密钥时才会被导入。**
面板上已经改过之后，secret 再 put 不会覆盖面板里的表 —— 以面板为准。
需要强制覆盖就先把面板里的都删光，再 put。

字段说明：

| 字段 | 含义 |
|---|---|
| `name` | 唯一名，也是配额计数的键 |
| `key` | 密钥本体 |
| `dayCalls` | 每日调用上限，不填 = 不限 |
| `dayBytes` | 每日字节上限，不填 = 不限 |
| `hosts` | 域名白名单，支持 `*.example.com`，不填 = 除私网外全放行 |

`hosts` 建议一定要填——等于给这把 key 划死能访问的范围，key 泄漏了损失也可控。

配额上限可以之后随时改：面板上「接出密钥」那一栏是唯一的真相来源，
`/api/me` 查的就是它。

### 面板上的管理接口

面板前端调的就是这几个（都在 `/admin/api/` 下面，需要管理员会话）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/admin/api/keys` | 列出全部密钥（含明文） |
| POST | `/admin/api/keys` | 新增或更新（`{name, key?, dayCalls, dayBytes, hosts}`，不传 key 就自动生成） |
| DELETE | `/admin/api/keys/<name>` | 吊销一把 |

注意两点：

- **同一把 key 不能挂在两个名字下**（返回 `duplicate_key`）。不然「撤一把」会连带影响另一把。
- 名字只允许字母数字下划线短横，最多 32 个字符（返回 `bad_name`）。

## 用这个出口伪造家庭住宅 IP

**目的已经达成。** 目标站看到的来源 IP，就是你家那条宽带：

```
本机直连    https://ip.3322.net            → 203.0.113.7
通过出口    GET /api/fetch?url=ip.3322.net → 203.0.113.7
目标站自报  httpbin.org/post 的 origin      → 203.0.113.7
```

`203.0.113.7` 是江西电信家庭宽带出口（`cdn-cgi/trace` 实测 `warp=off`、`loc=CN`）。
凡是**按 IP 判定**的风控——机房段拦截、只放行国内 IP、要求住宅 IP——这一层**完全成立**。

### 唯一不够用的一层：TLS 指纹

有的站不只看 IP，还看你**怎么握的手**（JA3/JA4 指纹）。ESP32 用 mbedtls，
握手特征一眼就是"嵌入式设备"，这类站会判"这不是普通住宅用户"。

| 判定维度 | 现状 |
|---|---|
| IP 是不是住宅 | ✅ 已经是 |
| UA / header 像不像浏览器 | ✅ 可自定义（下面有模板） |
| **TLS 指纹像不像浏览器（JA3/JA4）** | ❌ 改不了，除非换出口设备 |
| **HTTP/2 指纹** | ❌ 改不了（不会 ALPN，只能 HTTP/1.1） |

**大多数签到、内容、开放 API 只判 IP + UA + Cookie，这套够用，不用改。**
只有明确做了 JA3 指纹风控的站点（支付、银行、部分大站）才会卡到这一层。

#### 实测数据（不是引二手结论）

在本机起一个探针，从 TCP 层直接读 ClientHello 字节自己算 JA3
（`test/ja3-probe.py`，设备走管理路径抓本机即可）：

设备（ESP32-C6，mbedtls）：
```
TLS 版本   : 1.2
密码套件数 : 81
扩展数     : 7
扩展列表   : [0(sni), 10(supported_groups), 13(sig_algs), 11(point_formats),
              22(encrypt_then_mac), 23(ext_master_secret), 35(session_ticket)]
曲线       : [14, 29, 23, 24, 25, 26, 27, 28]
JA3        : 167c2cc233aa23a621d3c29e6962659c
```

同一台机器上的 Windows curl（schannel）：
```
密码套件数 : 20
扩展数     : 11
扩展列表   : [43, 13, 35, 10, 11, 16(ALPN), 51(key_share), 49(psk_kex),
              23, 65281(renegotiation_info), 45(padding)]
曲线       : [6, 29, 23, 24]
JA3        : f690f7e1fd527f931ddc496310a59925
```

差异集中在四处，每一处都足以被识别：

1. **81 个密码套件**。浏览器只发 10~20 个。mbedtls 把所有支持的套件全列出来，
   这是它最显眼的特征，TLS 指纹库里一眼就能匹配。
2. **扩展只有 7 个，而且没有 ALPN(16)**。没有 ALPN 就协商不了 h2 → 只能 HTTP/1.1，
   而现代浏览器几乎全是 HTTP/2。Akamai 那种 HTTP/2 指纹直接对不上 ——
   **这是 JA3 之外同样改不了的第二层**。
3. **没有 padding(45)**。浏览器用 padding 扩展把 ClientHello 撑到固定长度，mbedtls 不做。
4. **扩展顺序不同**。JA3 对顺序敏感，即使套件列表凑巧接近，哈希也完全不同。

JA4 把扩展排序后再哈希，能吃掉第 4 条差异，但前三条（套件数、缺 ALPN、无 padding）照样暴露。

#### 一个说法上的更正

「一眼就是嵌入式设备」—— 更准确的说法是：**一眼就不是浏览器**。

风控不需要认出「这是块 ESP32」，只要匹配到「这不是任何主流浏览器的 ClientHello」就行。
这反而更麻烦：mbedtls 的 JA3 是公开可查的（各类 TLS 指纹库都有收录），
风控把它归类成「自动化客户端 / 爬虫」直接降权，连是不是嵌入式设备都懒得区分。

#### 为什么改不了

- Arduino-ESP32 **3.x 硬编码 mbedtls**，平台预编译库里没有 bearssl 可选。
- 要改 JA3 得自己重编译 mbedtls（改套件列表、扩展顺序、开启 padding），Arduino core 不提供。
- 换 bearssl 能改一部分，但那只存在于 ESP-IDF 裸机工程，代价是重写整个网络层。
- **把 TLS 终结挪回 Worker 也不行** —— 那样设备就退化成纯 TCP 通道，
  而 Worker 出站用的是 Cloudflare 的 IP，家宽这个核心价值直接没了。

### 真要改的时候：把出口从 ESP32 换成家里那台机器

不用动固件。家里那台机器自己发请求就行：

- IP 还是同一条家宽 → 住宅属性不变
- TLS 栈换成系统自带的 → 指纹是真实 Windows/Chrome，JA3 认不出来
- 顺带解掉 ESP32 的 128KB 响应上限、并发 1、单次 1~12 秒三个限制

代价是那台机器要开着。代码上的改动就是：把"经出口抓"换成"在本机直接 fetch"，
ESP32 这条链路留给纯 IoT 场景。

### header 怎么配才像浏览器

关键不是把 UA 写成 Chrome，而是**让 UA 和 header 自洽**。缺一半比不改更容易露馅。

```js
import { createExit } from './sdk/exit-fetch.mjs';

const exit = createExit({ key: 'sk_项目专属key' });

const UA = 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 '
         + '(KHTML, like Gecko) Chrome/138.0.0.0 Safari/537.36';

const res = await exit.get('https://target.example/api/data', {
  headers: {
    'user-agent': UA,
    'accept': 'application/json, text/plain, */*',
    'accept-language': 'zh-CN,zh;q=0.9,en;q=0.8',
    'sec-ch-ua': '"Chromium";v="138", "Not=A?Brand";v="24", "Google Chrome";v="138"',
    'sec-ch-ua-mobile': '?0',
    'sec-ch-ua-platform': '"Windows"',
    'sec-fetch-dest': 'empty',
    'sec-fetch-mode': 'cors',
    'sec-fetch-site': 'same-origin',
    'referer': 'https://target.example/',
  },
});
```

三条规矩：

1. **UA 的浏览器版本要和 `sec-ch-ua` 对得上**。UA 写 138、`sec-ch-ua` 写 131，比不改更容易被识别。
2. **`sec-fetch-site` 要符合真实关系**：同站导航是 `same-origin`，外链跳进来是 `cross-site`。写错等于自曝。
3. **别每次换 UA**。同一把 key 一段时间用同一套画像，比每次随机更不像机器人。

### 接完先验一次

```js
const exit = createExit({ key: 'sk_项目专属key' });

// IP 归属：org 应该是中国电信，hosting 应该是 false
console.log(await (await exit.get('https://ipinfo.io/json')).json());

// 目标站把你当成什么浏览器
console.log(await (await exit.get('https://ip.useragentinfo.com/json')).json());

// 你实际发出去的 header，自己确认没被改
console.log(await (await exit.get('https://httpbin.org/headers')).json());
```

`hosting` 若是 `true`，说明目标站用的那个情报库把这条线当机房，在它眼里这条出口就不算住宅。
（后两个是境外服务，从家宽出去响应慢属正常。）

### 一条不能忽略的边界

设备→目标这一段**不校验证书**（固件 `setInsecure()`）。
带 Cookie 或任何身份信息走这个出口，等于**明文**发给你家路由器和 ISP 所在的那张网。
**这个出口只配用于公开内容**；带登录态的抓取必须先解决证书校验（见文末遗留）。

另一条边界跟权限有关：

| 入口 | 是否拦内网地址 |
|---|---|
| `POST /api/fetch`（对外，给其他项目用） | ✅ 拦（`checkTarget`，私网/回环/链路本地/云元数据） |
| `POST /admin/api/call`（管理面板） | ❌ **不拦** |

也就是说，**持有 `ADMIN_TOKEN` 的人可以让设备去抓任意内网地址**（路由器管理页、NAS、
其它智能家居的接口）。这是有意留给管理员的诊断能力，但它意味着：

> **`ADMIN_TOKEN` 不只是「能看面板」，它等同于「能通过你家设备访问内网」。**
> 这个口令绝对不能外泄，也不能写进任何第三方项目的代码里。

两条路径的策略不一致是有意为之：对外路径面对的是「可能被拿到 key 的第三方」，
必须假设最坏情况；管理路径面对的是管理员本人。
## 哪些项目适合接

| 适合 | 理由 |
|---|---|
| 抓第三方新闻 / RSS / 网页存档，且被云 IP 限流 | 低频、只读、内容公开 |
| 调只对国内 IP 开放的 API | 家宽是纯国内住宅 IP，比机房 IP 干净 |
| 验证「从用户侧看到的是什么」 | 家宽视角 ≈ 真实用户视角 |

| 不适合 | 理由 |
|---|---|
| 需要登录态的抓取 | 传不了 Cookie 之外的东西是一回事，UA 被识别是更大的问题 |
| 高并发 / 批量爬 | capacity=1，100 个请求排队 50 秒起步 |
| 图片/视频/大文件 | 128KB 上限 |
| 任何「不能失败」的生产链路 | 家里断电、路由器重启、ISP 抽风，它跟着没 |

## 当前遗留

只剩一条，而且是个设计取舍，不是 bug：

| 项 | 说明 |
|---|---|
| 设备→目标不校验证书 | 固件里 `sc.setInsecure()`。设备抓目标时不验证对端证书，所以运营商/路由器理论上能篡改返回的内容。**抓公开网页无所谓；抓任何带身份的东西（需要 Cookie、需要登录态）之前必须先解决。** 彻底解决要么在设备上放全量根证书（C6 内存和 flash 都吃紧），要么把 TLS 终结挪到 Worker（那就失去了「从家里出去」的意义） |

已修掉的（固件 2.1.0，2026-10-25）：
自定义 UA 写死、`content-type` 丢失、截断不上报、截断判定漏洞（提前退出不算截断）、
抓取期间心跳停摆导致假离线、`delay(1)` 轮询白等。

## 附录：自己验 TLS 指纹

上面那组 JA3 数据可以自己复现，探针在 `test/ja3-probe.py`：

```bash
cd F:/esp32/tunnel
PY="C:/Users/Administrator/.workbuddy/binaries/python/envs/default/Scripts/python.exe"

# 1) 自签证书（设备不校验目标证书，自签即可）
openssl req -x509 -newkey rsa:2048 -keyout tmp/ja3key.pem -out tmp/ja3cert.pem \
  -days 2 -nodes -subj "/CN=192.168.1.10"

# 2) 起探针（监听 8443，读 ClientHello 自己算 JA3）
$PY test/ja3-probe.py 8443 tmp/ja3cert.pem tmp/ja3key.pem

# 3) 让设备抓它 —— 走管理路径，那条路不做内网拦截
curl -H "Authorization: Bearer $ADMIN_TOKEN" -H "content-type: application/json" \
  -d '{"tool":"https_fetch","args":{"host":"192.168.1.10","port":8443,"path":"/","tls":true}}' \
  https://exit.example.com/admin/api/call

# 探针会打印设备那一份 ClientHello 的 JA3。
# 想知道本机浏览器的长什么样，第 3 步换成：
#   curl -sk https://192.168.1.10:8443/
```
